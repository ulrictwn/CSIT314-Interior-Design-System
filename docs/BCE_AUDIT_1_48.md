# BCE audit — User Stories 1–48, document version (5)

Source: `Nothinghere/CSIT314 Group Project Report (5).docx`. All 48 embedded BCE diagrams were inspected in story order. Diagram image hashes and independent method signatures are recorded in `docs/bce_contracts.json`. Version (5) changes the Story 4 diagram to include `displayError()` and corrects Story 42’s Category label; the other 46 diagram images are identical to version (4).

## Layer responsibilities

- Boundaries receive HTTP form/query/JSON values, strip ordinary text, call controllers, and prepare displays. Password whitespace is preserved.
- Controllers relay calls and results. Operation entities remain available through `controller.entity` for the boundary to read errors. There is no field validation, SQL, or copying of entity errors in controllers.
- Entities validate required fields, lengths, formats, supported values, identifiers, dates, duplicates, references, and saved state, then query/save data. Validation is performed inside the entity operations, including direct-call paths.

## Redundant code removed

- Controller duplicate-existence wrappers were removed; `userProfileExists` and `userAccountExists` remain in their entities as specified.
- Repeated update/delete confirmation getters were replaced by calls to the existing View controllers. Dropdown and unfiltered-list reads use the shared directory controller. Interest labels use the shared interest controller.
- Fifteen obsolete boundary constructors and the ignored explicit account-ID context argument were removed. The signed session supplies account context.
- Unused `UserProfile.profileName`, `UserProfile.viewUserProfile`, `UserAccount.is_admin`, and `Report.periodEndDate` helpers/aliases were removed. Private helpers still needed by actual queries/transactions remain.
- Story 2 uses inline missing-record presentation. Account suspension/report pages keep their runtime error display private where the diagrams do not list a public displayError operation.

## Runtime support retained

Flask needs get/post adapters, and operation controllers need constructors to retain their entity. Working forms also need prefill, confirmation, dropdown, directory, dashboard, serialization, and error-display support. These are identified separately from diagram story operations.

The one additional public method in a diagram controller is `UpdateUserProfileController.getUserProfile`, retained because it was explicitly requested for Story 3 prefill. All other diagram boundary/controller public operations match their respective diagrams after excluding get/post adapters. The diagram-private `incrementViewCount` and `categoryExists` methods are invoked inside entities.

Getter annotations include `| None` to represent missing records. Successful return types match the diagram types, and missing records produce the existing error displays.

## Story 6 and default passwords

The boundary, controller, and entity now follow `createUserAccount(username, password, fullName, email, phoneNumber, profileId)` (the boundary event is named onCreate). The create form still has no password input. Its POST adapter supplies `password`, which the entity accepts as the classroom default and stores as a hash. Trusted bootstrap callers pass their chosen private password in the same argument position. No password argument is removed from the diagram contract.

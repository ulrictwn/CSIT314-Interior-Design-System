# BCE audit — all 48 user stories

Source: `Nothinghere/CSIT314 Group Project Report (6).docx`. Reviewed on **10 November 2026**. All 48 freshly extracted BCE images match the independently transcribed image hashes and 208 method entries in [bce_contracts.json](bce_contracts.json). Story descriptions, flows and test-check lists were compared too. The TDD section explicitly says validation moved from boundaries into entities.

This audit applies the lecturer's rule: **boundaries strip input and display, controllers communicate, and entities validate all data and perform database work**. It corrects the earlier boundary-validation cleanup.

## Responsibilities

| Layer | Responsibility |
| --- | --- |
| Boundary | Receive form/query/JSON values, strip ordinary text, call the controller, and display results/errors. Preserve password whitespace. |
| Controller | Relay arguments and results. Keep the operation entity available for displaying errors. No field validation, database queries or copied error state. |
| Entity | Validate required fields, lengths, formats, choices, IDs, numeric values, searches, dates, credentials, duplicates, references, assignments, membership and saved state before database changes. |

`boundary/validation.py` contains only `strip_input`. Shared pure rules live in `entity/validation.py`; they have no Flask or database dependency. Entities call these rules for HTTP and direct Python callers. The unused `infrastructure/validation.py` copy was removed. Boundaries display entity errors without repeating the checks.

## Simplification and necessary runtime support

The existing diagram operations retain their names, parameter order/types and returns, including void event/display methods. Flask get/post adapters return `self.rendered_page`; constructors retain entities and account context. Private error-setter and New/Past CRUD dispatcher helpers remain inlined into the diagram operations. Methods keep short explanations and import-source notes.

Initial directories, dropdowns, prefill, confirmation, dashboards, serialization and CSV downloads need runtime support outside the diagrams. `UpdateUserProfileController.getUserProfile` remains as explicitly requested. `ViewUserProfileController.listUserProfiles` relays `UserProfile.listUserProfiles` for initial lists/dropdowns, because the diagram's submitted profile search must reject blank input in the entity. Account/category directory searches already permit blank input. No default-argument or blank-search bypass is added to the profile diagram method.

The Staff/Customer selector is an approved frontend feature. `StaffLoginController.selectRole` relays validation to `UserAccount.staffRole`; the boundary chooses the login page from the validated result. Other necessary support covers password setup/reset, role context, ownership, shortlist removal/membership and stored-report lookup/download. Existing role and ownership behavior is preserved. No new security features were introduced.

`ActivityEvent` retains the dated project-creation and shortlist-save history required by reports. This correction changes no columns, constraints, relationships or recording behavior. No migration or data reset is required.

## Document conflicts and agreed choices

- **Story 6:** Normal Flow still says the admin enters a password, but updated TC23 specifies the automatic default `password`. Preserve the approved password-free form and hashed default; POST supplies the diagram's password argument. CU101 is explicitly an example, so existing profile-based IDs are preserved.

- **Story 30:** Normal Flow includes pasted User Admin/account-view steps. Customer search follows its own story, diagram and TC47.

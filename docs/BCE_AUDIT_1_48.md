# BCE audit — all 48 user stories

Source: `Nothinghere/CSIT314 Group Project Report (5).docx`. Reviewed on **10 November 2026**. All 48 freshly extracted BCE diagram images match the independently transcribed image hashes and 208 method entries in [bce_contracts.json](bce_contracts.json). The story descriptions, normal/alternate flows, wireframes and test-check lists were also compared with the implementation.

This audit applies the latest requested split: **boundaries validate user input, controllers communicate, and entities validate saved data and perform database work**.

## Responsibilities

| Layer | Responsibility |
| --- | --- |
| Boundary | Receive form/query/JSON input, strip ordinary text, validate required fields, lengths, formats, choices, IDs, numbers and dates inside the diagram event; display results/errors. Preserve password whitespace. |
| Controller | Relay arguments and results. Keep the operation entity available to the boundary for errors. No field validation, database queries, or copied error state. |
| Entity | Validate duplicate names/emails/registrations, references, ownership-related data, assignments, membership and saved state; query, save, commit or roll back. Reuse essential pure checks for direct Python/CLI callers. |

`boundary/validation.py` exposes field checks to HTTP handlers. The reusable pure rules have one implementation in `infrastructure/validation.py`; they import no Flask or entity models and query no database. The five old entity validation modules were removed. This keeps boundary validation visible in onCreate/onUpdate/onSearch/onLogin/onGenerate... without duplicating the rules.

## Method simplification and explanations

The six `_reject` helpers were removed from UserProfile, UserAccount, CompanyProfile, InteriorDesignProject, Category and Shortlist. Each diagram operation now assigns its error details and returns False directly. The email, registration, project-name and keyword query helpers were folded into the operations that use them. New/Past create/update/get/search/delete dispatcher helpers were also removed; the diagram methods contain the relevant work themselves. Required getters are reused by update/delete operations.

All **409 application methods/functions** now start with a short explanation. Local application imports have comments identifying the source file and purpose; method notes identify imported dependencies where they help trace the BCE call. For example, CreateUserProfilePage.onCreate points to boundary/validation.py and control/profile/create_user_profile_controller.py, whose controller points to entity/profile/user_profile.py.

Required runtime helpers remain for named-role setup, password reset/login, session role selection, serialization, shortlist membership/removal, ownership checks, dashboards and stored-report lookup/downloads. These helpers preserve working flows without adding arguments to unrelated diagram methods. The unused MonthlyReportController constructor endDate state and unused local_today function were removed. No model columns, data or diagram signatures changed.

## Necessary runtime support

Flask needs get/post adapters; controllers need constructors to retain entities and required account/date context. Initial lists, prefill, confirmation, dropdowns, dashboards, HTML/JSON formatting and CSV downloads remain necessary for the supplied flows. Entity operations now contain their own error handling, duplicate queries and New/Past database work, so those operations can be followed directly in the diagram methods. ActivityEvent retains dated creation/shortlist history required by the reports.

Boundary and controller public story operations match the diagrams after excluding Flask adapters. The sole retained extra public story-controller method is UpdateUserProfileController.getUserProfile, explicitly requested for update prefill. Getter return annotations allow None for missing records. Event/display handlers remain void and store their HTTP result in self.rendered_page.

## Document conflicts and agreed choices

- Story 6 prose mentions password entry, while TC23 says no initial password. The approved password-free form and hashed default password `password` are retained. Its BCE password argument is supplied by POST. The CU101 account ID is an example; existing IDs remain based on the actual profile ID and shared sequence.
- Profile update follows the diagram arguments and preserves status. Suspension uses its own diagram operation. Your requested removal of the View sidebar entries and View buttons in suspend lists remains in effect.
- Story 20 prose mentions project dates, but its BCE signature and test data have no date parameters. The six diagram fields are retained.
- Story 30 includes pasted User Admin/account-view steps. Customer IDP search follows its own story, BCE diagram and test.
- Story 41 says an active IDP must exist before creating a category. That would create a category/project bootstrap cycle and contradict its empty-category test. Category creation requires the manager login and valid category data.
- Story 44 refers to deleting a profile within the category flow; the implementation deletes the selected unused category.
- Report TC63–TC65 still list login/registration totals. As agreed, reports follow the updated use cases/wireframes: new IDPs created, shortlist-save actions and top category by new IDPs. Code tests reflect these figures.

The Word file has not been rewritten. These conflicts are recorded rather than silently changing diagrams or introducing speculative fields.
